**Summary:** Strata's installer and build system reject anything below sm_80, but the
kernels appear to have pre-Ampere code paths. Could sm_70 (V100, T4) be supported?

## What I hit

`setup.sh` stops with "not supported - older than the RTX 30 series" on a V100, and
`CMakeLists.txt` has a matching arch guard. So the published install path is closed
before anything else happens - including before the model download starts.

## Why I think it is close to working

The attention kernels carry `#if __CUDA_ARCH__ >= 800` guards, but they do have older
branches underneath: `qsa_select.cu`, `qsa_prompt_attn.cu` and `native_qsa_score.cu`
all fall back, and those paths work on sm_70 (slower, but correct). With these opened
I got a fully working, numerically correct install:

1. the installer's arch gate (`setup.py`, `gpu_problem`)
2. the CMake arch guard
3. the device qualification check in `src/core/device.cu`
4. `Q6_K` dispatch in the IQ expert kernels (`src/kernels/cuda/iq_kernels.cu`)
5. multi-shard GGUF discovery - see below
6. `HF_ENDPOINT` override for `tools/mtp_fetch.py`

Point 5 is worth separating out, because I think it is an actual bug rather than a
platform issue: `--gguf-dir` builds the shard list as exactly
`<model>-00001-of-00002.gguf` and `<model>-00002-of-00002.gguf`. Artifacts named
differently or sharded differently (e.g. Unsloth's `-00001-of-00003`) are not found.
Deriving the count from the `-0000N-of-` part of the filename, as the engine and
`tools/iq_pack.py` already do, would make it work.

## Measured on 2x V100-SXM2-16GB (PCIe, no NVLink), Xeon E5-2680 v4

| | |
|---|---|
| decode | 43.4 tok/s (MTP `--spec 2 --spec-min-p 0.5`, Chinese, draft acceptance 77-78%) |
| decode, no MTP | 35.2 tok/s |
| prefill | 865 tok/s on a 117,088-token prompt (135 s) |
| context | 131072, verified with a needle at ~58K tokens, right at the layer-split boundary |

The CPU is the bottleneck on this machine (no AVX-512, no VNNI): the expert pool is
~70% of each decode step. A CPU with AVX-512 should be considerably faster.

## What I am asking

1. Would you consider accepting sm_70, and if so, would you gate it as "best effort"
   rather than in the main support matrix?
2. What would you need from me to make it safe - a CI job on sm_70 hardware I do not
   have, or is a documented "this is what I measured" enough?
3. Should the `--gguf-dir` shard-count fix (point 5) go in regardless of the platform
   question? It is independent of GPU architecture.
